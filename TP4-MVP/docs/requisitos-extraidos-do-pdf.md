## Síntese dos requisitos observados

O enunciado define o **TP4 como a construção de um MVP funcional e navegável** do aplicativo escolhido, com um conjunto mínimo de funcionalidades que valide o conceito da solução e mantenha coerência com os artefatos das etapas anteriores do trabalho.

O documento informa que a equipe pode usar o **Figma Make como ponto de partida** para geração inicial de telas, componentes e estrutura do sistema, mas determina que o sistema seja **obrigatoriamente evoluído e aprimorado pela equipe**, com desenvolvimento no **Visual Studio Code**, modificações próprias, melhorias sobre a geração inicial, funcionalidades efetivamente implementadas e demonstração de entendimento técnico do código produzido.

## Requisitos obrigatórios do MVP identificados nas páginas 1 a 5

| Tema | Requisito identificado |
|---|---|
| Objetivo do TP4 | Entregar uma versão funcional e navegável do aplicativo, validando conceito e solução. |
| Coerência | Manter alinhamento com artefatos produzidos nas etapas anteriores do TP. |
| Evolução técnica | O material inicial deve ser evoluído pela equipe, não apenas reproduzido. |
| Ambiente de desenvolvimento | O enunciado cita evolução do projeto no Visual Studio Code. |
| Quantidade mínima de telas | O MVP deve conter no mínimo 8 telas. |
| Tela obrigatória 1 | Tela de cadastro de usuário com armazenamento de dados, validação de campos, mensagens de feedback e exibição/aceite de Termos de Uso e Política de Privacidade. |
| Tela obrigatória 2 | Tela de login com autenticação, mensagens de erro/sucesso, acesso aos termos e política e presença obrigatória da logo do aplicativo. |
| Demais telas | Outras telas essenciais do aplicativo devem ser relacionadas entre si e permitir navegação implementada. |
| Navegação | O documento menciona navegação implementada, incluindo menus, botões e acesso sequencial entre telas. |
| Rastreabilidade | Para cada funcionalidade implementada, deve ser indicada a história de usuário correspondente e uma breve explicação de como foi implementada. |

## Exemplo explícito de rastreabilidade mostrado no PDF

O PDF apresenta um exemplo com a história de usuário H6, descrevendo uma pessoa doadora em potencial que deseja se cadastrar e receber por e-mail um guia com orientações de uso para iniciar o processo de doação de forma segura e informada. O exemplo reforça que cada funcionalidade do MVP deve ser vinculada a uma história de usuário e acompanhada de uma breve explicação de implementação.

## Complemento de requisitos extraídos das páginas 6 a 10

As páginas finais do PDF acrescentam exigências explícitas de **refatoração, gerência de configuração, controle de versão, organização do repositório e entregáveis finais**.

### Requisitos adicionais identificados

| Tema | Requisito identificado |
|---|---|
| Refatoração | A equipe deve aplicar **pelo menos 5 refatorações distintas** no código do projeto. |
| Documentação das refatorações | Cada refatoração deve registrar: problema identificado, motivação, descrição da melhoria e impacto no sistema. |
| Histórico GitHub | As refatorações devem estar registradas no histórico do GitHub com commits descritivos e organizados. |
| Gerência de configuração | O projeto deve aplicar práticas básicas de gerência de configuração em fluxo estruturado de trabalho colaborativo. |
| Fluxo sugerido | Clonar, desenvolver, commitar, pushar e atualizar. |
| Controle de versão | Devem ser seguidas convenções claras para commits, branches e merges. |
| Padrão de commits | O PDF exemplifica commits como `feat: adiciona tela de login`, `refactor: reorganiza autenticação` e `docs: atualiza README`. |
| Branches obrigatórias | O PDF exemplifica o uso de `main`, `develop` e `refactor/nome-da-refatoracao`. |
| Merge | O fluxo indicado inclui merge visual da branch, integração das alterações à branch develop e manutenção do histórico organizado. |
| Versionamento do MVP | Deve ser criada pelo menos uma release/tag da versão MVP, com exemplo `v1.0-mvp`. |
| Estrutura do repositório | O PDF recomenda diretórios como `docs/`, `prints/`, `video/` e uma árvore clara de código-fonte. |
| Entrega final | O resumo das entregas cita MVP funcional, histórico GitHub e ao menos 5 refatorações documentadas no repositório. |

### Trechos relevantes observados

> "A equipe deverá aplicar pelo menos 5 refatorações distintas no código do projeto, baseadas no catálogo de refactorings do livro de Engenharia de Software Moderna."

> "Todas as refatorações deverão estar registradas no histórico do GitHub com commits descritivos e organizados."

> "Criar pelo menos uma release/tag da versão MVP."

> "Todas as equipes deverão apresentar os seguintes itens na entrega final do TP4: MVP Funcional, Histórico GitHub, Refatorações."

### Implicações práticas para o TP4-MVP

O diretório `TP4-MVP` não deve conter apenas o código do aplicativo. Ele também precisa deixar explícitos os elementos de avaliação: documentação de rastreabilidade, documentação das cinco refatorações, termos de uso, organização de diretórios compatível com o PDF e evidências do processo de versionamento no GitHub. Mesmo quando alguma etapa de Git não puder ser concluída automaticamente no ambiente, o repositório deve ser preparado de forma coerente para suportar esse fluxo.
